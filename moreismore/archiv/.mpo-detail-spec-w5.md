## F.1/F.2 — TTS via MCP-Tool (neuer Ansatz)

**Prioritaet:** HOCH — volle Sprachschleife ist Kern-Feature

### Bisheriger Ansatz (gescheitert)
VoiceOutputRouter (voice-output-router.ts) pollt Session-Output per `sessionManager.capture()` alle 500ms, erkennt Stabilisierung, strippt ANSI-Codes, sendet an PiperTTS.
→ Fragil: tmux-Output enthaelt Tool-Calls, ANSI-Codes, Claude-UI-Chrome. Parsing unzuverlaessig.

### Neuer Ansatz: MCP-Tool `mux_tts_speak`

**Konzept:** Die Entity entscheidet BEWUSST was vorgelesen wird. Kein passives Mitlesen.

**Vorteile:**
- Entity kuratiert: Code-Bloecke, Tool-Output, Debugging-Text fliessen durch OHNE vorgelesen zu werden
- Kein fragiles Output-Parsing noetig
- Latenz kontrollierbar (Entity kann Satz fuer Satz senden)
- Funktioniert mit ALLEN Entities, nicht nur Voice-Relay

### Tool-Definition (in mcp-tools.ts, am Ende)

```typescript
// mux_tts_speak — Text vorlesen lassen
{
  name: 'mux_tts_speak',
  description: 'Speak text via TTS. Use this to read responses aloud to the user.',
  inputSchema: {
    type: 'object',
    properties: {
      text: { type: 'string', description: 'Text to speak aloud' },
      priority: {
        type: 'string',
        enum: ['normal', 'interrupt'],
        description: 'normal = queue, interrupt = stop current speech and play immediately'
      }
    },
    required: ['text']
  }
}
```

### Backend-Flow

1. MCP-Tool `mux_tts_speak` empfaengt Text
2. Text an `conversationEngine.speakResponse(text)` oder direkt an `piperTTS.speak(text)`
3. PiperTTS rendert Audio → spielt ab
4. Bei `priority: 'interrupt'`: laufende Wiedergabe stoppen, neuen Text sofort abspielen

### VoiceOutputRouter Anpassung

Der VoiceOutputRouter wird **nicht mehr fuer TTS gebraucht** (sein Polling-Ansatz wird durch das MCP-Tool ersetzt). Optionen:
1. VoiceOutputRouter behalten aber nur noch fuer Event-Emission (kein TTS-Routing)
2. Oder komplett deaktivieren wenn `mux_tts_speak` aktiv ist

**Empfehlung:** VoiceOutputRouter beibehalten fuer nicht-MCP-faehige Sessions (z.B. Plain-Sessions ohne Claude), aber Default-Path ist jetzt das MCP-Tool.

### Entity-CLAUDE.md Instruktion
Alle Entity-CLAUDE.md muessen wissen: "Nutze `mux_tts_speak` um dem User Antworten vorzulesen. Lies NICHT alles vor — nur die Kernaussage. Kein Code, keine Tool-Outputs, keine Debug-Infos vorlesen."

→ **WICHTIG:** Das erfordert Koordination mit Worker 2 (E.4 CLAUDE.md-Rewrites). Sage dem MPO Bescheid dass du eine TTS-Instruktion brauchst die in alle Entity-CLAUDE.md eingefuegt wird.

**VoiceControl.tsx:**

- Leuchtet/gedimmt je nach Pin-State

**SessionCell.tsx (Header):**

## F.4 — STT sendet an Hintergrundsession statt fokussierte

**Schwere:** KRITISCH

### Symptom
STT-Output wird an eine Hintergrundsession geschickt statt an die fokussierte Grid-Session.

### Aktueller Code (voice-input-router.ts Z.53-160)
`setFocusedSession(sessionId)` wird aufgerufen wenn der User eine Session fokussiert. Aber:
1. Wann wird `setFocusedSession` aufgerufen? Vermutlich beim Grid-Cell-Klick.
2. Wird es auch aufgerufen wenn eine Session in den Hintergrund geht?
3. Wenn eine Session in den Hintergrund geht und keine neue fokussiert wird, zeigt `focusedSessionId` noch auf die alte (jetzt Hintergrund-) Session.

### Loesung
1. `setFocusedSession(null)` wenn aktive Session in den Hintergrund geht
2. `setFocusedSession(newId)` wenn andere Session fokussiert wird
3. Validation in `routeToSession()`: Pruefen ob `focusedSessionId` noch eine Grid-Session ist (nicht Hintergrund)

### Akzeptanzkriterien
- [ ] STT sendet AUSSCHLIESSLICH an fokussierte Grid-Session
- [ ] STT sendet NICHT an Hintergrundsessions
- [ ] Wenn keine Session fokussiert: STT-Text wird verworfen (nicht in Limbo geschickt)

## F.5 — STT Leerzeichen nach Segment fehlt

**Schwere:** Mittel

### Symptom
Beim Diktieren fehlen Leerzeichen zwischen Whisper-Segmenten wenn User kurz pausiert.

### Aktueller Code
voice-input-router.ts sendet den transkribierten Text direkt via `sendKeys()`. Kein Leerzeichen-Handling zwischen Segmenten.

### Loesung
Nach jedem STT-Segment ein Leerzeichen anhaengen bevor es per sendKeys geschickt wird:
```typescript
const textToSend = transcript.trimEnd() + ' '
await this.sessionManager.sendKeys(sessionId, textToSend)
```

### Akzeptanzkriterien
- [ ] Aufeinanderfolgende Segmente haben Leerzeichen dazwischen
- [ ] Kein doppeltes Leerzeichen bei Segmenten die bereits mit Space enden

## F.6 — BugReport-Popup z-Index und STT-Ablauf

**Schwere:** Mittel

### Drei Probleme

**1. z-Index:** Info-Popup schwebt UEBER dem BugReport-Popup.
→ BugReport-Popup z-Index erhoehen (muss ueber Info-Dialog liegen).

**2. STT-Pause unzuverlaessig:** STT sollte bei BugReport-Open sofort deaktiviert werden.
→ Event-Handler: `onBugReportOpen` → `voiceManager.pauseSTT()`

**3. STT resumed nicht:** Nach Schliessen kehrt STT nicht zum vorherigen Zustand zurueck.
→ `onBugReportClose` → `voiceManager.resumeSTT()` (nur wenn vorher aktiv war)

### Erwarteter Ablauf
1. BugReport auswaehlen → STT aus (pauseSTT)
2. BugReport-Popup oeffnet sich (Voice deaktiviert)
3. User erfasst Report
4. Popup schliessen
5. Falls vorher STT an: STT wird wieder aktiviert (resumeSTT)

### Akzeptanzkriterien
- [ ] BugReport-Popup liegt ueber allen anderen Popups (z-Index)
- [ ] STT pausiert automatisch bei BugReport-Open
- [ ] STT resumed automatisch bei BugReport-Close (wenn vorher aktiv)
