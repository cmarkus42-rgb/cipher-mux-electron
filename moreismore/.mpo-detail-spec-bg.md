## Kontext

**Symptom:** MCP-Tools verschwinden waehrend laufender Session ohne erkennbaren Trigger. "No such tool available." Alle Tools gleichzeitig betroffen. Erfordert App-Neustart.

**Bisheriger Fix (Commit 9187e1d):**
- Timeout von 30min auf 4h erhoeht
- Keep-Alive Headers
- Error-Handler fuer req/res
- lastActivity Update auf Response-Finish

**Problem:** Passiert weiterhin (mindestens 2x am 2026-04-28).

---

## Untersuchungsplan

### Phase 1: Log-Analyse (30 Min)

1. **MCP-Server-Logs pruefen:** Gibt es Transport-Close/Error-Events zur Zeit des Drops?
   - `mcp-server.ts` Z.154-159: Transport error/close Logging
   - Suche nach "transport closed", "transport error", "GC: removing stale session" in App-Logs

2. **Timing:** Korreliert der Drop mit:
   - Langer Inaktivitaet (>10 Min)?
   - Spezifischen Tool-Calls?
   - Netzwerk-Aenderungen (WiFi-Wechsel, Sleep/Wake)?
   - macOS App Nap?

3. **Session-GC:** Wird die Session per Sweep gekillt obwohl sie aktiv ist?
   - `sweepStaleSessions()` Z.352-364: Prueft `lastActivity`
   - Moeglich: lange Tool-Execution → keine Requests → lastActivity veraltet → GC killt Session

### Phase 2: Upstream-Analyse (30 Min)

1. **Claude Code Reconnect-Verhalten:**
   - Was passiert wenn der MCP-Server kurz nicht erreichbar ist?
   - Reconnected Claude Code automatisch?
   - Gibt es ein Timeout nach dem Claude Code aufgibt?

2. **HTTP Transport-Spezifika:**
   - StreamableHTTPServerTransport — haelt das eine lange Verbindung oder macht es neue Requests?
   - Kann ein einzelner HTTP-Timeout den gesamten MCP-Client kaputt machen?

### Phase 3: Workaround-Optionen (60 Min)

**Option A: Health-Check + Auto-Reconnect**
- Periodischer Health-Check vom Main-Prozess: "Kann die Session noch MCP-Tools aufrufen?"
- Bei Failure: MCP-Server Session-Entry loeschen → Client wird bei naechstem Request neue Session initialisieren
- Risiko: Kann die Client-Seite (Claude Code) mit einer neuen Session umgehen?

**Option B: Robustere GC**
- GC nur wenn Session WIRKLICH inaktiv (kein offener Response-Stream)
- `lastActivity` auch bei langen SSE-Streams aktualisieren
- Ping-Endpoint den der Client periodisch callt

**Option C: Session-Restart-Mechanismus**
- Wenn Drop erkannt: Automatisch `claude --resume` in der tmux-Session ausfuehren
- Problem: Session hat dann keine MCP-Tools mehr (braucht neuen `claude` Start mit MCP-Config)

**Option D: Monitoring + Alerting**
- Drop erkennen und User sofort benachrichtigen (Sidebar-Warning)
- Manual-Reconnect-Button in Session-Header
