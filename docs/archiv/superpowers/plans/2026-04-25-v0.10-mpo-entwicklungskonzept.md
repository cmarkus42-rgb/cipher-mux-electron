## Sub-Projekt-Details

### SP-1: i18n Foundation
**Scope:** i18next + preact-i18next einrichten, EN als Primary, DE als zweite Sprache. Alle ~150-200 bestehenden UI-Strings extrahieren. Sprachumschaltung in Settings. JSON-Dateien pro Sprache.
**Beruehrt:** `src/renderer/` (alle Komponenten), `src/shared/` (neue i18n-Config), Settings-Page
**Konflikt-Risiko:** HOCH mit allem was Renderer-Komponenten aendert → muss in Wave 1 fertig sein bevor Wave 2 startet

### SP-2: Notes MCP + Handoff
**Scope:**
- Notes CRUD vervollstaendigen: `mux_notes_read`, `mux_notes_update`, `mux_notes_search`, `mux_notes_delete`
- **NEU: Session-Handoff via Notes** — Uebergabe-Prompts zwischen Sessions als Notes ablegen (Tag: `handoff`, Frontmatter: `from_session`, `to_entity`, `context`). Entity-Sessions lesen Handoff-Notes automatisch beim Start wenn verfuegbar. Ermoeglicht nahtlose Session-Uebergaben ohne Copy-Paste.
**Beruehrt:** `src/main/notes/`, `src/main/mcp/tools/`, `src/shared/types.ts`
**Konflikt-Risiko:** NIEDRIG (eigenes Modul)

### SP-3: Entity Framework + Visual Highlighting
**Scope:**
- `EntityConfig` Interface + Entity-Registry (Companion, Refinement, Orchestrator, MPO, Launcher)
- `SessionManager.startEntity(entityId)` — generalisiert bestehende startOrchestrator/startMpo
- **Linkliste + StatusBar:** Companion + Refinement als direkt startbare Sessions in LauncherCell-Linkliste UND StatusBar-Buttons (gleichrangig mit Orchestrator/MPO)
- Companion: CLAUDE.md + Guides + Refs aus `the how-to-session/` nach `~/.config/cipher-mux/entities/companion/`
- Refinement: CLAUDE.md + Skills + Brain aus `the refinement session/` nach `~/.config/cipher-mux/entities/refinement/`
- Entity-spezifische Farben/Badges im PaneHeader (inkl. MPO-Highlighting aus Phase 5a)
- Recovery-Support per Entity-Name
- **Handoff-Integration:** Entity-Sessions pruefen beim Start auf Handoff-Notes (Tag `handoff`, `to_entity` match) und injizieren Kontext automatisch
**Beruehrt:** `src/main/session/`, `src/renderer/components/StatusBar`, `src/renderer/components/PaneHeader`, `src/shared/types.ts`
**Konflikt-Risiko:** MITTEL (SessionManager, StatusBar)

### SP-4: Companion Memory System
**Scope:**
- SQLite-Schema: memories, memories_fts, user_profile, persona_state, pending_updates (aus SPEC.md)
- MemoryStore: write(), recall(), search(), forget() mit FTS5
- 4 MCP-Tools: `companion_memory_write`, `companion_memory_recall`, `companion_memory_search`, `companion_memory_forget`
- Persona-Injector: dynamische SKILL.md-Generierung fuer Relay
- relay-core.md Template + Renderer
- Info-Popup: How-to-Content aus externer .md-Datei (3d)
- CompanionMemoryView in Sidebar: Timeline + Suchfeld (3d)
- Sidebar-Tab "Memory" (3d)
**Beruehrt:** `src/main/companion/` (NEU), `src/main/mcp/tools/`, `src/renderer/components/`, `src/shared/`
**Konflikt-Risiko:** NIEDRIG (hauptsaechlich neue Dateien), MITTEL fuer 3d (Sidebar/Renderer)
**Hinweis:** 3d (Memory UI) braucht SP-3's Entity-System fuer die Sidebar-Integration. SP-4 arbeitet 3b+3c zuerst ab, 3d kommt wenn SP-3 fertig ist.

### SP-5: Session Management

### SP-7: Voice Relay Session (Post-Plateau)
**Konzept:** Eigener Button in Linkliste/StatusBar → startet eine **dedizierte Background-Session** als sprachgesteuertes Relay. Nicht einfach ein Voice-Toggle auf dem Companion, sondern eine eigenstaendige 6. Entity mit speziellem Profil.

**Was Voice Relay kann:**
- **Sprachkanal:** VAD → Whisper STT → Claude-Session-Input → Response → Piper TTS (bidirektional, hands-free)
- **MCP-Operator:** Voller Zugriff auf alle cipher-mux MCP-Tools — kann aktiv in andere Sessions eingreifen:
  - `mux_send` — Befehle/Fixes in Worker-Sessions schicken
  - `mux_read` — Output anderer Sessions vorlesen/zusammenfassen
  - `mux_create_session` / `mux_kill_session` — Sessions starten/stoppen
  - `mux_status` / `mux_context_usage` — Ueberblick geben
  - `mux_notes_*` — Wissen nachschlagen und ablegen
  - `companion_memory_*` — Erinnerungen abrufen und speichern
- **How-to-Wissen:** Gesamtes Companion-Guideset (Guides + Refs aus `the how-to-session/`) als Kontext. Kennt alle cipher-mux-Features und kann den User durch Workflows fuehren.
- **Relay-Persona:** Gleiche Persona wie Text-Companion, aber auf natuerliches Sprechen getrimmt (laengere Saetze, Konversationston, keine Code-Bloecke in Sprach-Output)

**Session-Architektur:**
- Entity-Typ: `voice-relay` in Entity-Registry
- Erscheint als normale Background-Session in Sidebar (wie Orchestrator)
- Kein Grid-Slot noetig (laeuft headless im Hintergrund)
- StatusBar: Mikrofon-Icon mit Zustandsanzeige (idle/listening/speaking)
- Shared Memory: Gleicher Companion Memory Store wie Text-Companion + Refinement
- System-Prompt: Relay-Persona + How-to-Guides + explizite MCP-Tool-Instruktionen ("Du kannst Sessions manipulieren, hier ist wie...")

**Beispiel-Interaktionen:**
- "Hey Relay, was macht die Orchestrator-Session gerade?" → liest Output, fasst zusammen
- "Schick dem Worker mal den Fix fuer den Import-Fehler" → `mux_send` an Worker
- "Starte eine neue Session fuer das Frontend" → `mux_create_session`
- "Wie funktioniert das mit den Workspaces?" → How-to-Guide abrufen, erklaeren
- "Merk dir dass wir uns fuer Option B entschieden haben" → `companion_memory_write`

**Beruehrt:** `src/main/voice/`, `src/main/session/`, Entity-Registry, StatusBar (Mic-Widget)
**Aufwand:** ~2d (Voice-Pipeline existiert, Hauptarbeit = Session-Architektur + System-Prompt + StatusBar-Widget)
**Konflikt-Risiko:** NIEDRIG (baut auf fertigem Entity-System + Memory auf)
**Startet erst nach Plateau-Feedback**

### SP-9: Workspace-Persona-Prompt-Optimierung (Wave 2, Subagent)
**Konzept:** Dedizierte Optimierungssession fuer die **Workspace-Persona-Prompts** — die Templates die via `persona-skill-sync` als SKILL.md in Sessions injiziert werden. Nicht die Entity-CLAUDE.md System-Prompts, sondern die Persona-Definitionen die das Verhalten der Claude-Sessions in Workspaces steuern.

**Scope — Workspace-Persona-Templates reviewen und optimieren:**
- **relay-core.md** — Shared Persona Core Template (`{{display_name}}`, `{{user_profile_yaml}}`, `{{evolved_annotations}}`). Das Herzstueck — definiert Charakter, Stil, Ton fuer alle Relay-basierten Sessions.
- **Builtin-Persona "Relay"** — Default-Persona-Definition die beim ersten Start geseeded wird. Aktuell minimal, kann viel mehr.
- **Persona-Rendering-Pipeline** — Wie `persona-injector.ts` / `persona-skill-sync.ts` den finalen SKILL.md-Output zusammenbauen. Subagent prueft ob die Template-Variablen optimal genutzt werden.
- **Entity-spezifische Persona-Overlays** — Companion (Advisor), Refinement (Ideation), Voice Relay (Konversation) brauchen jeweils eigene Overlay-Prompts die auf relay-core aufbauen.

**Optimierungs-Ziele:**
- **Tiefe statt Floskeln:** Konkrete Verhaltensanweisungen mit Beispielen statt "sei hilfreich und freundlich"
- **Ton-Kalibrierung:** "Ruhig, kompetent, leicht nerdig, trockener Humor" — mit konkreten Do/Don't-Beispielen unterfuettern
- **User-Profil-Nutzung:** Wie Relay das User-Profil (Level, Background, History) nutzt um Antworten anzupassen — aktuell kaum ausgeschoepft
- **Memory-Integration:** Wann und wie Relay den Memory Store nutzen soll (Recall-Cues, Write-Heuristiken)
- **MCP-Tool-Awareness:** Welche Tools verfuegbar sind und wann Relay sie proaktiv einsetzen soll vs. nur auf Anfrage
- **Entity-Grenzen:** Klare Abgrenzung was jede Spezialisierung tut und was nicht (Companion beratet, orchestriert nicht; MPO delegiert, codet nicht)
- **Konsistenz:** Alle Persona-Varianten fuehlen sich wie dieselbe Person an, nur mit anderem Fokus

**Arbeitsweise:**
- Subagent liest bestehende Persona-Templates + persona-skill-sync Code
- Analysiert was aktuell gerendert wird vs. was moeglich waere
- Erstellt optimierte Templates als .md-Dateien
- Liefert Changelog pro Template (was geaendert, warum, vorher/nachher)

**Beruehrt:** `.md`-Template-Dateien, ggf. kleine Anpassungen in `relay-render.ts` fuer neue Template-Variablen
**Aufwand:** ~0.5-1d
**Konflikt-Risiko:** SEHR NIEDRIG (hauptsaechlich .md-Dateien)
**Abhaengigkeit:** `needs-decision-from` SP-3 (Entity-Struktur + Overlay-Mechanismus muss klar sein), kann parallel zu SP-4/5/6 laufen

### SP-10: Doku & How-to Aktualisierung (Wave 3, Routine)
**Konzept:** Abschluss-Phase die nach jeder groesseren Aenderungswelle laufen soll — wird zur Routine. Bringt alle nutzergerichtete Dokumentation auf den aktuellen Stand.

**Scope:**
- **Info-Fenster (Features-Tab):** Wiki-Eintraege in `InfoSettingsView.tsx` aktualisieren — neue Entities (Companion, Refinement, Voice Relay), neue Features (Handoff, Memory, Folder-Picker), aktualisierte Shortcuts

**Beruehrt:** `.md`-Dateien, `InfoSettingsView.tsx` (Wiki-Content)
**Aufwand:** ~0.5-1d (skaliert mit Aenderungsumfang)

## Handoff-Feature (Neu, User-Request)

### Konzept
Session-Uebergaben werden als Notes gespeichert statt als Copy-Paste-Bloecke:

1. **Schreiben:** Wenn eine Session endet oder eine Uebergabe ansteht, erstellt sie eine Handoff-Note:
   ```yaml
   ---
   title: "Handoff: v0.10 MPO Zerlegung"
   tags: [handoff]
   from_session: cmux-mpo-main
   to_entity: mpo          # oder "any" fuer allgemeine Uebergaben
   created: 2026-04-25T14:30:00
   ---
   Naechste Schritte:
   1. Plan + Memory lesen
   2. Sub-Projekt-Aufteilung erstellen
   ...
   ```

2. **Lesen:** Integrierte Entity-Sessions (Companion, Refinement, MPO, Orchestrator) pruefen beim Start:
   - `mux_notes_search(tags: ['handoff'], to_entity: self.entityId)`
   - Gefundene Handoff-Notes werden als Kontext injiziert
   - Nach Verarbeitung: Note wird als `consumed` getaggt (nicht geloescht)

3. **UX-Flow:**
   - User sagt "erstell eine Uebergabe" → Session schreibt Handoff-Note
   - User startet neue Session desselben Entity-Typs → Handoff wird automatisch geladen
   - User sieht im Sidebar-Notes-Tab die Handoff-Notes mit speziellem Badge

### Einordnung
- Notes-CRUD (SP-2) liefert die Infrastruktur (`mux_notes_search` mit Tag-Filter)
- Entity-Framework (SP-3) implementiert den Auto-Read beim Session-Start
- Kein eigenes Sub-Projekt noetig — verteilt sich auf SP-2 und SP-3

## Risiko-Analyse

| Risiko | Wahrscheinlichkeit | Impact | Mitigation |
|---|---|---|---|
| i18n-String-Extraktion dauert laenger (>200 Strings) | Mittel | SP-1 verzoegert | Wave 2 startet trotzdem, neue Strings i18n-konform |
| SessionManager-Konflikte SP-3/SP-5 | Mittel | Merge-Aufwand | Interface-First: SP-3 definiert EntityConfig, SP-5 konsumiert |
| Context-Limit bei SP-6 (viele kleine Items) | Niedrig | Session stuck | Items sind isoliert, ggf. Session neu starten fuer letzte Items |
| SPEC.md-Luecken bei Memory-Implementation | Mittel | SP-4 blockiert | SPEC + 4 ADRs liegen vor, offene Punkte im KICKOFF.md adressiert |
| Voice Relay Architektur-Komplexitaet (Entity + Voice + MCP) | Mittel | SP-7 verzoegert | Entity-System + Voice-Pipeline existieren, Hauptarbeit = Verkabelung + System-Prompt |
