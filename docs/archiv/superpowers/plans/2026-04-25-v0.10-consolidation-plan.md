## Leitidee: Die 5 Entitaeten von cipher-mux

cipher-mux liefert 5 integrierte Funktions-Sessions ("Entitaeten") aus:

| Entitaet | Rolle | Relay-Spezialisierung | Status |
|---|---|---|---|
| **Orchestrator** | Koordiniert Worker-Sessions | Relay als Dispatcher | Existiert (v0.9.x) |
| **Project Launcher** | Projekt-Kickoff + Interview | Relay als Interviewer | Existiert (v0.9.x) |
| **MPO** | Multi-Projekt-Zerlegung | Relay als Generalunternehmer | Existiert (v0.9.x) |
| **Companion** (ex "how-to-session") | Lehrt, beratet, begleitet | Relay als Advisor | Zu integrieren |
| **Refinement** | Idee → Requirements | Relay als Ideation-Partner | Zu integrieren |

**Alle 5 teilen die Relay-Persona** — gleicher Charakter (ruhig, kompetent, leicht nerdig, trockener Humor), unterschiedliche funktionale Spezialisierung. Die Persona-Definition ist identisch, der System-Prompt spezialisiert.

**Alle 5 teilen das persistente Gedaechtnis** — der Companion Memory Store ist das Langzeitgedaechtnis von Relay ueber alle Entitaeten hinweg. "Weisst du noch was wir gestern gemacht haben?" funktioniert egal ob der User gerade im Companion, Refinement oder Orchestrator sitzt.

**Alle 5 teilen das User-Profil** — `~/.config/cipher-mux/user-profile.json` (existiert bereits in how-to + refinement).

## Phase 1: i18n Foundation (Frontloading)

**Tickets:** GCQ8Q9, XPB9Q6 (Duplikat)
**Warum zuerst:** Jedes neue Feature danach produziert automatisch i18n-konforme Strings. Rueckwaerts-Migration wird exponentiell teurer.

### Scope
- i18n-Framework einrichten (z.B. `i18next` + `preact-i18next` oder leichtgewichtiger Custom-Ansatz)
- EN als Primaersprache, DE als zweite Sprache
- Alle bestehenden UI-Strings extrahieren (~150-200 Strings geschaetzt)
- Sprachumschaltung in Settings
- Backend/Storage bleibt EN (nur Frontend-Strings)
- Architektur: JSON-Dateien pro Sprache, dynamisch ladbar ohne Rebuild

### Abgrenzung
- Keine CLAUDE.md/Persona-Templates uebersetzen (die bleiben in der Sprache die der User/Autor waehlt)
- Relay-Sessions sprechen Deutsch (Persona-Eigenschaft, nicht i18n)
- Kein automatisches Language-Detection — User waehlt explizit

### Aufwand-Schaetzung: 1.5-2d

## Phase 2: Notes MCP Vollausbau

**Ticket:** D8D39K
**Abhaengigkeit fuer:** Phase 3 (Relay braucht Notes-CRUD fuer Wissensablage)

### Scope
Bestehende MCP-Tools (`mux_notes_create`, `mux_notes_list`) erweitern um:
- `mux_notes_read` — Note by ID lesen (Frontmatter + Body)
- `mux_notes_update` — Note editieren (Title, Tags, Body — partiell oder komplett)
- `mux_notes_search` — Volltextsuche ueber Notes (grep-basiert oder FTS)
- `mux_notes_delete` — Note loeschen

### Kontext
Alle Relay-Entitaeten nutzen Notes als geteilte Wissensschicht:
- Refinement speichert Requirements als Notes (macht es schon)
- Companion speichert Guides/How-tos
- Orchestrator/MPO koennen Status-Zusammenfassungen als Notes ablegen
- Der Memory Store (Phase 3) ist separat — Notes sind das "explizite" Wissen, Memory das "implizite"

### Aufwand-Schaetzung: 1d

## Phase 3: Relay Entity System (Kern-Feature)

**Tickets:** ZETVTX, 1QW09A, PJBRHX, YG4ZD7, N3FHEN, KPHBQW, feature-companion-subsystem.md
**Das Killer-Feature.** Spec + ADRs + KICKOFF.md liegen bereit.

```
                    ┌─────────────────────────┐
                    │    Relay Persona Core    │
                    │  (Charakter, Stil, Ton)  │
                    └─────────┬───────────────┘
                              │
              ┌───────────────┼───────────────┐
              │               │               │
    ┌─────────▼──┐  ┌────────▼───┐  ┌────────▼────────┐

              └───────────────────────┘
```

### Sub-Phasen

**3a — Entity Framework + Session Integration (1.5d)**

Generalisiertes System fuer Funktions-Sessions (nicht nur Companion):

- `EntityConfig` Interface: name, displayName, persona, templatePath, startupGreeting, features[]
- Entity-Registry: Companion, Refinement (neu), Orchestrator, MPO, Launcher (bestehend migrieren)
- SessionManager: `startEntity(entityId)` — generalisiert startOrchestrator/startMpo
- StatusBar: Buttons fuer alle Entitaeten (Companion + Refinement neu, Orchestrator + MPO migrieren)
- Recovery-Support per Entity-Name
- Grid-Placement wie bisher (naechster freier Slot, PlacementPopup bei vollem Grid)

**Companion-Spezifika:**
- Rename: "Coding Companion" ueberall im UI
- Pre-filled Greeting: "Hey, kannst du mir was erklaeren?"
- CLAUDE.md + Guides + Refs aus `the how-to-session/` integrieren (nach `~/.config/cipher-mux/entities/companion/`)

**Refinement-Spezifika:**
- CLAUDE.md + Skills + Brain aus `the refinement session/` integrieren (nach `~/.config/cipher-mux/entities/refinement/`)
- Startup-Greeting angepasst (aus Profil, wie in Refinement-CLAUDE.md definiert)

**3b — Companion Memory Store (1.5d)**

Das persistente Gedaechtnis von Relay, geteilt ueber alle Entitaeten:

- SQLite-Schema: memories (id, entity, session_id, user_message_summary, relay_action, context_tags, created_at)
- FTS5 Virtual Table fuer Volltext-Retrieval
- MemoryStore: write(), recall(), search(), forget()
- Automatisches Memory-Writing: Anhaltspunkte notieren wenn Relay mit dem User interagiert
- Recall on-demand: per MCP-Tool, kein statisches Injection in Kontext
- **Plateau 1:** FTS5-basiertes Retrieval (einfach, robust, testbar)

**3c — MCP Memory Tools (0.5d)**

4 neue MCP-Tools, verfuegbar fuer alle Entitaeten:
- `companion_memory_write` — Erinnerung speichern (entity, summary, context_tags)
- `companion_memory_recall` — Letzte N Erinnerungen abrufen (optional: entity-Filter, Zeitraum)
- `companion_memory_search` — FTS5-Suche ueber Erinnerungen
- `companion_memory_forget` — Erinnerung loeschen (User-Kontrolle)

**3d — Info-Popup + UI (0.5d)**
- Info-Popup: How-to-Content aus externer .md-Datei laden (`~/.config/cipher-mux/entities/companion/how-to-info-popup.md`)
- Editierbar ohne Rebuild (File-Watch oder Reload-Button)
- CompanionMemoryView in Sidebar: Timeline der Erinnerungen, Suchfeld
- Sidebar-Tab: "Memory" (neben Sessions, Notes, Messages)

**3e — TTS-Chat fuer Companion (1d)**

Conversational Voice-Mode speziell fuer den Companion:
- Eigene Voice-Session: VAD → Whisper → Companion-Input → Response → Piper TTS
- Auf natuerliches Reden getrimmt (eigener Kontext, laengere Antworten als im Coding-Modus)
- Piper-Integration existiert bereits (Bugreport-Interview), wird wiederverwendet
- **Nicht** die app-weite Voice-Steuerung (das ist Fernziel Barrierefreiheit)

### Plateau nach 3a-3d: Freitesten

Nach Sub-Phase 3d ist das Entity-System funktional:
- Companion + Refinement starten per Button
- Memory wird geschrieben und kann abgerufen werden
- Notes-CRUD funktioniert via MCP

**Hier Pause fuer User-Feedback und Freitesten bevor 3e (TTS) und hoehere Memory-Features (Embeddings, Pending-Queue) kommen.**

### Aufwand-Schaetzung: 5d (3a-3d: 4d, 3e: 1d nach Plateau)

## Phase 4: Session Management

**Tickets:** BAEXXR, SXMDW8, 2EE9XA (Research-Teil)

- `StartSessionOpts` um `resume?: boolean` erweitern
- Alle Entity-Sessions (Orchestrator, MPO, Companion, Refinement) standardmaessig mit `--resume`
- UI: Resume-Option im Session-Dialog fuer manuelle Sessions

### 4b — Fork Session (0.5d)
- Fork-Button im PaneHeader (neben bestehenden Controls)
- `claude --fork-session --resume <session-id>` ausfuehren
- Forked Session in naechstem freien Grid-Slot, Name: `<original>-fork`

### 4c — Verwaiste Sessions einsammeln (Research → ggf. Impl)
- Forschungsauftrag: tmux-Sessions ohne cipher-mux-Zuordnung erkennen
- `tmux list-sessions` vs. bekannte `cmux-` Prefixes abgleichen
- UI: "Orphaned Sessions" Hinweis in Sidebar, Click → adoptieren
- **Scope-Grenze:** Nur verwaiste cipher-mux-Sessions (nach Crash etc.). Externe Terminals bleiben aussen vor.
